__Naming Convention Standard__

__استاندارد نام‌گذاری پایگاه داده، کد و API__

__Version: 1.0 (Frozen)__

__1. هدف سند__

این سند به منظور ایجاد یک استاندارد یکپارچه برای نام‌گذاری اجزای سیستم ERP شامل پایگاه داده، کد نرم‌افزار، API و اجزای زیرساختی تهیه شده است.

هدف اصلی جلوگیری از نام‌گذاری سلیقه‌ای، افزایش خوانایی، کاهش خطاهای توسعه و ایجاد هماهنگی بین تیم‌های توسعه، نگهداری و توسعه‌دهندگان آینده است.

تمامی توسعه‌های جدید باید مطابق این استاندارد انجام شوند.

__بخش اول: استاندارد نام‌گذاری Database__

__اصل 1 - زبان نام‌گذاری__

تمامی نام‌های مربوط به Database باید به زبان انگلیسی باشند.

استفاده از کلمات فارسی، مخفف‌های نامفهوم یا نام‌های وابسته به افراد و پروژه‌ها ممنوع است.

__اصل 2 - استاندارد Case در Database__

تمامی اجزای Database شامل:

- Table
- Column
- Index
- Constraint
- View
- Function

باید از استاندارد Snake Case استفاده کنند.

قواعد:

- تمام حروف کوچک باشند.
- فاصله با Underline جدا شود.
- استفاده از PascalCase یا camelCase در Database ممنوع است.

__بخش دوم: استاندارد Table Naming__

__اصل 3 - نام جداول__

نام تمام جداول باید به صورت جمع (Plural) نوشته شود.

هدف:

- نمایش صحیح اینکه جدول شامل مجموعه‌ای از موجودیت‌ها است.
- هماهنگی با استانداردهای رایج ORM و Database Design.

__اصل 4 - استاندارد Primary Key__

نام Primary Key همیشه بر اساس نام مفرد موجودیت (Singular Entity Name) ساخته می‌شود.

الگو:

singular_entity_name \+ _id

Primary Key نباید از نام جمع جدول استفاده کند.

__اصل 5 - Foreign Key Naming__

نام Foreign Key باید بر اساس نام موجودیت مرجع ساخته شود.

الگو:

referenced_entity_name \+ _id

تمامی Foreign Keyها باید دارای نام واضح و قابل تشخیص باشند.

__بخش سوم: Column Naming__

__اصل 6 - نام ستون‌ها__

نام ستون‌ها باید:

- واضح
- کوتاه
- قابل فهم
- بدون مخفف غیر استاندارد

باشد.

__اصل 7 - ستون‌های زمانی__

تمامی ستون‌های زمانی باید دارای نام مشخص باشند.

قواعد:

- زمان ایجاد:

created_at

- زمان آخرین تغییر:

updated_at

- زمان حذف نرم:

deleted_at

__اصل 8 - ستون‌های کاربران عملیاتی__

ستون‌های مربوط به ایجادکننده و تغییر دهنده اطلاعات باید استاندارد زیر را داشته باشند:

created_by

updated_by

deleted_by

__بخش چهارم: استاندارد Soft Delete و Versioning__

__اصل 9 - حذف نرم__

حذف فیزیکی اطلاعات عملیاتی ممنوع است.

تمامی جداول عملیاتی باید قابلیت Soft Delete داشته باشند.

ستون استاندارد:

deleted_at

deleted_by

__اصل 10 - Row Version__

تمامی جداولی که نیاز به کنترل همزمانی دارند باید دارای:

row_version

باشند.

__بخش پنجم: استاندارد جداول واسط__

__اصل 11 - Many To Many Tables__

نام جداول واسط باید از ترکیب نام موجودیت‌ها ساخته شود.

قانون ترتیب:

اولویت با موجودیت اصلی (Parent) و سپس موجودیت وابسته (Child) است.

در صورت نبود رابطه Parent/Child، ترتیب الفبایی استفاده می‌شود.

__بخش ششم: Index و Constraint Naming__

__اصل 12 - استاندارد Index__

نام Index باید مشخص‌کننده جدول و ستون مربوطه باشد.

الگوی کلی:

idx_table_column

__اصل 13 - استاندارد Unique Index__

Unique Index باید با پیشوند زیر ساخته شود:

uq_

__اصل 14 - استاندارد Foreign Key Constraint__

نام Constraintهای ارتباطی باید دارای الگوی مشخص باشند.

هدف:

- تشخیص سریع رابطه
- ساده شدن نگهداری Database

__بخش هفتم: View و Function__

__اصل 15 - استاندارد View__

تمام Viewها باید با پیشوند زیر شروع شوند:

vw_

__اصل 16 - استاندارد Function__

تمام Functionها باید با پیشوند زیر شروع شوند:

fn_

__بخش هشتم: استاندارد Naming در Code__

__اصل 17 - تفکیک Database و Code__

استاندارد Snake Case فقط برای Database است.

در کدنویسی باید از استاندارد زبان برنامه‌نویسی استفاده شود.

قواعد عمومی:

__Class__

PascalCase

__Variable و Method__

camelCase

__بخش نهم: استاندارد API__

__اصل 18 - API Versioning__

تمام APIها باید نسخه‌بندی داشته باشند.

هدف:

- جلوگیری از شکست سرویس‌های وابسته
- امکان توسعه مستقل ماژول‌ها

__اصل 19 - API Route Naming__

مسیرهای API باید با استاندارد:

kebab-case

نوشته شوند.

استفاده از:

- Snake Case
- Pascal Case

در Routeها ممنوع است.

__بخش دهم: قوانین نهایی کنترل__

__اصل 20 - ممنوعیت تصمیم‌گیری سلیقه‌ای__

هیچ توسعه‌دهنده، تیم یا ماژولی اجازه ندارد خارج از این استاندارد نام‌گذاری انجام دهد.

هر تغییر در این استاندارد باید:

1. ثبت شود.
2. بررسی معماری شود.
3. نسخه جدید سند ایجاد کند.
