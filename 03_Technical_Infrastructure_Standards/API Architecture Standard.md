__استاندارد معماری API__

__API First Architecture Standard__

__نسخه سند:__ 1.0  
__وضعیت:__ Freeze شده برای طراحی و توسعه پروژه ERP SaaS

__1. هدف سند__

این سند مجموعه قوانین و استانداردهای طراحی، توسعه و استفاده از API در پلتفرم ERP SaaS را تعریف می‌کند.

هدف اصلی این استاندارد:

- ایجاد یک قرارداد ارتباطی مشخص بین بخش‌های مختلف سیستم
- جلوگیری از وابستگی مستقیم بین ماژول‌ها
- حفظ قابلیت توسعه بلندمدت سیستم
- آماده‌سازی معماری برای رشد ماژولار و تبدیل احتمالی به معماری Microservice در آینده
- جلوگیری از پراکندگی منطق کسب‌وکار در لایه‌های مختلف سیستم

__اصل 1: API قرارداد رسمی ارتباط سیستم است__

تمام ارتباطات بین بخش‌های مختلف سیستم باید از طریق API انجام شود.

هیچ بخش خارجی یا داخلی سیستم اجازه ندارد برای دریافت یا تغییر اطلاعات، مستقیماً به دیتابیس یا ساختار داخلی یک ماژول دیگر دسترسی داشته باشد.

API تنها مرجع رسمی تعامل بین اجزای سیستم است.

__اصل 2: تفکیک API Layer از Business Logic الزامی است__

لایه API فقط مسئول موارد زیر است:

- دریافت درخواست
- اعتبارسنجی اولیه
- مدیریت ارتباط با مصرف‌کننده
- انتقال درخواست به لایه کسب‌وکار

لایه API نباید شامل:

- قوانین کسب‌وکار
- محاسبات تخصصی
- فرآیندهای ERP
- تصمیمات سازمانی

باشد.

منطق اصلی سیستم باید در لایه Business Logic قرار گیرد.

__اصل 3: عدم اتصال مستقیم Client به Database__

هیچ Client یا برنامه مصرف‌کننده‌ای اجازه اتصال مستقیم به Database را ندارد.

تمام عملیات:

- ایجاد اطلاعات
- خواندن اطلاعات
- ویرایش اطلاعات
- حذف اطلاعات

باید از طریق API انجام شود.

__اصل 4: هر ماژول باید API مستقل داشته باشد__

هر ماژول ERP باید Interface مشخص و مستقل خود را ارائه دهد.

ماژول‌ها نباید جداول داخلی یا ساختار دیتابیس خود را به عنوان روش ارتباطی در اختیار سایر بخش‌ها قرار دهند.

ارتباط صحیح:

Client / Module → API → Module Service

ارتباط ممنوع:

Module → Database Tables → Module

__اصل 5: تمام APIها باید Version داشته باشند__

تمام APIهای سیستم باید از ابتدا دارای نسخه باشند.

اهداف نسخه‌بندی:

- جلوگیری از شکستن مصرف‌کنندگان موجود
- امکان توسعه تدریجی
- حفظ Backward Compatibility
- امکان تغییرات کنترل‌شده در آینده

هیچ API بدون Version مجاز نیست.

__اصل 6: تغییرات API نباید باعث اختلال در سیستم موجود شود__

در صورت تغییر ساختار API:

- نسخه قبلی باید تا زمان مناسب حفظ شود.
- تغییرات ناسازگار نباید روی نسخه فعال اعمال شود.
- فرآیند مهاجرت باید کنترل شده باشد.

__اصل 7: منطق کسب‌وکار فقط در Backend معتبر است__

هیچ مصرف‌کننده‌ای مانند Frontend یا سیستم خارجی نباید منطق کسب‌وکار را پیاده‌سازی کند.

تمام قوانین مربوط به:

- محاسبات
- اعتبارسنجی
- محدودیت‌ها
- فرآیندها
- تصمیمات سازمانی

باید در Backend اجرا شوند.

__اصل 8: کنترل دسترسی فقط از Core Identity انجام می‌شود__

هیچ ماژولی اجازه ایجاد سیستم Authorization مستقل ندارد.

تمام بررسی‌های مربوط به:

- User Permission
- Role
- Scope
- Tenant Access

باید توسط سیستم مرکزی Identity & Access انجام شود.

ماژول‌ها فقط نتیجه دسترسی را مصرف می‌کنند.

__اصل 9: تمام APIها باید Tenant Aware باشند__

با توجه به معماری Shared Database Multi Tenant:

تمام APIهای عملیاتی باید Tenant جاری را مشخص و کنترل کنند.

هیچ API اجازه ندارد بدون تعیین Tenant:

- اطلاعات بخواند
- اطلاعات ایجاد کند
- اطلاعات تغییر دهد

نشت اطلاعات بین Tenantها (Data Bleed) خط قرمز سیستم است.

__اصل 10: ارتباط بین ماژول‌ها باید Loose Coupled باشد__

ارتباط بین ماژول‌ها نباید باعث وابستگی سخت شود.

موارد ممنوع:

- دسترسی مستقیم به جداول ماژول دیگر
- وابستگی به ساختار داخلی دیتابیس
- وابستگی به کلاس‌ها و پیاده‌سازی داخلی ماژول‌ها

روش‌های مجاز:

- API Contract
- Event Contract
- Logical Reference

__اصل 11: ساختار پاسخ API باید استاندارد باشد__

تمام APIها باید از الگوی پاسخ یکسان استفاده کنند.

خروجی API باید شامل موارد استاندارد باشد:

- وضعیت عملیات
- داده خروجی
- پیام
- اطلاعات خطا
- کد خطا

هدف، ایجاد رفتار یکسان در تمام APIهای سیستم است.

__اصل 12: مدیریت خطا باید استاندارد باشد__

خطاهای API باید:

- دارای کد مشخص باشند.
- قابل تشخیص توسط Client باشند.
- اطلاعات داخلی سیستم را افشا نکنند.
- پیام مناسب برای مصرف‌کننده داشته باشند.

__اصل 13: تمام APIها باید مستند باشند__

هر API باید دارای مستندات کامل باشد.

مستندات شامل:

- Endpoint
- Method
- ورودی‌ها
- خروجی‌ها
- خطاها
- سطح دسترسی
- نسخه API

باشد.

استاندارد مستندسازی:

OpenAPI Specification

__اصل 14: استاندارد نام‌گذاری API الزامی است__

مسیرهای API باید از استاندارد مشخص پیروی کنند.

قوانین:

- استفاده از kebab-case در Routeها
- استفاده از نام‌های مفهومی کسب‌وکار
- عدم وابستگی نام API به ساختار Database

API باید زبان Business Domain را نمایش دهد، نه ساختار جداول.

__اصل 15: API نباید ساختار داخلی سیستم را افشا کند__

مصرف‌کننده API نباید از موارد زیر اطلاع داشته باشد:

- نام جداول Database
- روابط داخلی Database
- ساختار ذخیره‌سازی اطلاعات
- جزئیات پیاده‌سازی داخلی

API یک قرارداد کسب‌وکاری است، نه نمایش Database Schema.

__اصل 16: عملیات حساس باید Audit شوند__

عملیات مهم سیستم باید قابلیت ثبت و پیگیری داشته باشند.

مانند:

- تغییر اطلاعات مالی
- تغییر سطح دسترسی
- تغییر تنظیمات مهم
- عملیات مدیریتی

__اصل 17: طراحی API باید توسعه‌پذیر باشد__

APIها باید امکان اضافه شدن موارد زیر را بدون تغییرات بنیادی فراهم کنند:

- ماژول‌های جدید
- Clientهای جدید
- Integrationهای جدید
- سرویس‌های آینده

__اصل 18: استفاده از Event برای ارتباطات غیرهمزمان__

برای فرآیندهایی که نیاز به پاسخ فوری ندارند، استفاده از Event پیشنهاد می‌شود.

موارد مناسب:

- Notification
- پردازش‌های سنگین
- هماهنگی بین ماژول‌ها
- عملیات پس‌زمینه

__اصل 19: معماری باید قابلیت استفاده از API Gateway را حفظ کند__

حتی اگر در نسخه اول سیستم Backend یکپارچه باشد، طراحی باید امکان استفاده از API Gateway در آینده را حفظ کند.

اهداف:

- مدیریت ورودی‌ها
- امنیت
- Routing
- مدیریت نسخه‌ها
- کنترل دسترسی

__اصل 20: هیچ بخشی اجازه دور زدن API را ندارد__

این قانون نهایی معماری است.

موارد زیر ممنوع هستند:

- خواندن مستقیم دیتابیس ماژول دیگر
- تغییر مستقیم اطلاعات خارج از سرویس مربوطه
- دور زدن قوانین Business Logic
- ایجاد مسیر ارتباطی خارج از API

تمام تعاملات سیستم باید از مسیرهای تعریف‌شده معماری انجام شود.
