۰. حاکمیت دستورالعمل‌ها و گردش کار عامل هوش مصنوعی (AI Agent Workflow & Governance)
این بخش، چارچوب مطلق تعامل بین کاربر و هوش مصنوعی را تعیین می‌کند و رعایت آن در اولویت بالاتر از تمام قوانین فنی قرار دارد.

قانون ۰.۱: اولویت مطلق قوانین و عدم نادیده‌گیری
هیچ‌گاه قوانین و دستورالعمل‌ها (چه در این فایل و چه در مخازن گیت مرجع) نادیده گرفته نمی‌شوند. هرگونه تناقض باید فوراً به کاربر گزارش شود.

قانون ۰.۲: تکمیل اجباری دانش از مخزن گیت (Context Fetching)
فایل rules.txt خلاصه‌ای از اسناد مهم و فقط حاوی "قوانین رفتاری" است و به هیچ وجه منبع کامل دانش فنی نیست. در ابتدای هر فرآیند توسعه یا ویرایش، هوش مصنوعی موظف است با دریافت دستور مخصوص، مخزن گیت اسناد معماری و پروژه را به‌طور کامل بررسی کند. 
⚠️ توجه: این فایل (rules.txt) فقط چارچوب رفتاری را یادآوری می‌کند؛ منبع اصلی و حقیقت مطلق (Single Source of Truth) برای وضعیت کد، وابستگی‌ها و ساختار پروژه، همواره مخزن گیت است.

قانون ۰.۳: بررسی دقیق وابستگی‌ها (بدون حدس و گمان)
توسعه یا ویرایش هر ماژول ممکن است در یک چت جدید آغاز شود. بررسی وابستگی‌ها به سایر بخش‌ها باید دقیقاً بر اساس خواندن فایل‌های واقعی مخزن گیت (به‌ویژه پایش مداوم پوشه‌های database, test, app) باشد و هرگونه فرضیه‌سازی ذهنی یا کار بر اساس احتمال اکیداً ممنوع است.

قانون ۰.۴: اصل خواندن قبل از ویرایش و ارائه کد کامل
قبل از هرگونه ویرایش، کد قبلی فایل در گیت باید خوانده شود تا منطق یا سیاست‌های موجود حفظ شود. ارائه کد به‌صورت تکه‌تکه (Snippet) یا دستور "این قسمت را جایگزین کن" اکیداً ممنوع است. هوش مصنوعی باید کد کامل و ویرایش‌شده‌ی فایل را ارائه دهد.

قانون ۰.۵: گردش کار عامل‌محور (Agent Workflow)
هوش مصنوعی باید کارها را دقیقاً در روال زیر انجام دهد:
  ۱. ارائه دستورات PowerShell برای ساخت فولدر/فایل (با شرط عدم بازنویسی مخرب یا حذف فایل‌های موجود).
  ۲. ارائه مسیر کامل فایل به همراه کد کامل ویرایش‌شده در یک بلوک کد واحد.
  ۳. ارائه دستورات Git با کامنت استاندارد و معنادار (به زبان انگلیسی) برای به‌روزرسانی مخزن در انتهای هر بخش.
  ۴. ارائه دستورات Docker در صورت نیاز به همگام‌سازی، بیلد یا اجرای سرویس‌ها.

قانون ۰.۶: آدرس‌های مرجع دسترسی
- مخزن اسناد معماری: https://github.com/akhlaghimhd/hamareh-erp-docs.git
- مخزن فایل‌های پروژه: https://github.com/akhlaghimhd/hamarehSaasErp.git

قانون ۰.۷: امنیت، تست و زبان
- در تولید اسکریپت‌ها، از قرار دادن مقادیر Secret، Password یا Token به‌صورت Hardcode خودداری شود.
- در صورت تغییر منطق کسب‌وکار، ایجاد یا به‌روزرسانی فایل‌های تست مرتبط در پوشه test الزامی است.
- کدها و پیام‌های Commit باید به زبان انگلیسی استاندارد باشند، اما توضیحات و گزارش‌ها برای کاربر به زبان فارسی ارائه شود.

۱. حاکمیت داده و ایزوله‌سازی چندمستأجری (Multi-Tenancy & Data Isolation)
این دسته غیرقابل مذاکره‌ترین بخش امنیت پلتفرم است.
قانون ۱.۱: تمام جداول عملیاتی ماژول‌ها باید دارای ستون tenant_id باشند (اصل Tenant Isolation By Design).
قانون ۱.۲: هیچ Query، API یا Service اجازه خواندن یا نوشتن داده بدون بررسی و محدود کردن tenant_id را ندارد. نشت اطلاعات بین مشتریان (Data Bleeding) خطای بحرانی معماری است.
قانون ۱.۳: استفاده از PostgreSQL RLS (Row Level Security) و Global Scopes در لایه اپلیکیشن برای ایزوله‌سازی اجباری است.
قانون ۱.۴: حذف فیزیکی اطلاعات عملیاتی ممنوع است. تمامی جداول عملیاتی باید قابلیت Soft Delete داشته باشند (ستون‌های deleted_at و deleted_by).
قانون ۱.۵: تمامی جداولی که نیاز به کنترل همزمانی (Concurrency Control) دارند، باید دارای ستون row_version BIGINT NOT NULL DEFAULT 1 باشند.
🔗 ۲. مرزبندی و ارتباط ماژول‌ها (Module Boundaries & Inter-Module Communication)
حفظ استقلال ماژول‌ها برای امکان مهاجرت آینده به Microservice.
قانون ۲.۱: هر ماژول یک Bounded Context مستقل است و مالک منطق و داده‌های دامنه خود است.
قانون ۲.۲: ایجاد کلید خارجی فیزیکی (Physical Foreign Key Constraint) بین جداول دو ماژول مختلف در دیتابیس اکیداً ممنوع است.
قانون ۲.۳: ارتباط بین ماژول‌های مستقل فقط باید از طریق: Logical Reference (UUID)، API، Domain/Integration Event یا Service Contract باشد.
قانون ۲.۴: استثنا: داخل یک Bounded Context (مثلاً بین fin_acc_journal_entries و fin_acc_journal_items) استفاده از Physical Foreign Key مجاز است.
قانون ۲.۵: در فاز Modular Monolith، ارتباطات همگام (Synchronous) بین ماژول‌ها نباید از طریق درخواست‌های شبکه HTTP API انجام شود؛ بلکه باید از طریق صدا زدن Service Contracts/Interfaces در حافظه هندل گردد.
🗄️ ۳. استانداردهای پایگاه داده و نام‌گذاری (Database & Naming Conventions)
قوانین سخت‌گیرانه برای خوانایی و هماهنگی تیم.
قانون ۳.۱: تمامی نام‌های Database باید به زبان انگلیسی باشند. استفاده از کلمات فارسی یا مخفف‌های نامفهوم ممنوع است.
قانون ۳.۲: تمامی اجزای Database (Table, Column, Index, Constraint, View, Function) باید از استاندارد Snake Case (تمام حروف کوچک و جدا شده با _) استفاده کنند. استفاده از PascalCase یا camelCase در دیتابیس ممنوع است.
قانون ۳.۳: نام تمام جداول باید به صورت جمع (Plural) نوشته شود (مثال: inv_warehouses).
قانون ۳.۴: نام Primary Key همیشه بر اساس نام مفرد موجودیت + _id ساخته می‌شود (مثال: warehouse_id).
قانون ۳.۵: ستون‌های زمانی استاندارد: created_at, updated_at, deleted_at. ستون‌های کاربر عملیاتی: created_by, updated_by, deleted_by.
قانون ۳.۶: پیشوندهای اجباری: ایندکس (idx_)، یونیک ایندکس (uq_)، ویو (vw_)، فانکشن (fn_).
قانون ۳.۷: منطق کسب‌وکار (Business Logic) نباید داخل Database قرار گیرد. استفاده از Trigger، Stored Procedure یا Function برای Business Logic ممنوع است (مگر با تصمیم رسمی معماری).
🔑 ۴. هویت، امنیت و کنترل دسترسی (Identity, Security & Access Control)
مدیریت متمرکز دسترسی‌ها.
قانون ۴.۱: اصل Core Only Once: هیچ ماژولی اجازه ایجاد سیستم Identity یا Authorization مستقل ندارد (مثلاً ساخت جدول inventory_permissions ممنوع است).
قانون ۴.۲: مدل دسترسی باید دقیقاً از این زنجیره پیروی کند: User → Role → Permission → Scope → Resource.
قانون ۴.۳: سیستم Scope باید تمام محدودیت‌های سطح دسترسی را مدیریت کند (مثل Company, Branch, Warehouse Scope). ماژول جدید نباید سیستم Scope جدید ایجاد کند.
قانون ۴.۴: هر Request ورودی باید شامل JWT Context امنیتی باشد که user_id, tenant_id, roles, scopes را حمل می‌کند.
🧩 ۵. حاکمیت داده‌های پایه (Master Data Governance)
جلوگیری از هرج‌ومرج در داده‌های مشترک.
قانون ۵.۱: هر موجودیت Master Data فقط یک مالک (Owner Module) دارد و نسخه واحد حقیقت (Single Source of Truth) است.
قانون ۵.۲: هیچ ماژولی مجاز به ایجاد نسخه مستقل یا کپی کردن اطلاعات پایه متعلق به ماژول دیگر نیست (مثلاً ماژول فروش حق ساخت جدول customers را ندارد، باید از Master Data استفاده کند).
قانون ۵.۳: Master Data به دو دسته تقسیم می‌شود:
Platform Master Data (بدون tenant_id، مثل Currency, Country)
Tenant-Owned Master Data (با tenant_id، مثل Items, Warehouses)
قانون ۵.۴: تمام Master Data ها باید از استاندارد Soft Delete و Audit Trail پیروی کنند.
⚙️ ۶. معماری فنی و چرخه حیات توسعه (Technical Architecture & Development Lifecycle)
استانداردهای کدنویسی و آماده‌سازی برای آینده.
قانون ۶.۱: معماری Backend بر اساس ترکیب Modular Monolith، Domain Driven Design (DDD) و Clean Architecture است.
قانون ۶.۲: ساختار استاندارد هر ماژول Backend باید شامل پوشه‌های: Domain, Application, Infrastructure, API باشد.
قانون ۶.۳: اصل API First: تمام ارتباطات بیرونی ماژول باید از یک لایه مشخص API انجام شود و APIها باید Versioned باشند (مثال: /api/v1/orders).
قانون ۶.۴: تمام APIها و Eventها باید نسخه‌بندی شوند (مثال: InvoiceCreated.v1) تا تغییر یک ماژول باعث شکستن سایر ماژول‌ها نشود (Backward Compatibility).
قانون ۶.۵: اصل Reuse Before Create: قبل از ایجاد هر جدول یا سرویس جدید، باید بررسی شود که آیا این قابلیت قبلاً در Core یا ماژول دیگری وجود دارد.
قانون ۶.۶: اصل Configuration Before Customization: قبل از توسعه اختصاصی برای یک مشتری، باید بررسی شود که آیا نیاز با Configuration، Setting، Feature Flag یا Workflow قابل حل است.
